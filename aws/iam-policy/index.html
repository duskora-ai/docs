IAM policy for the AWS integration

Last updated: 17 November 2026

Duskora connects to an AWS account with an IAM user's access key pair. An org admin adds it in Organization settings → Connections → AWS. Attach the policy below to that IAM user before connecting it. Settings checks the key against this policy and names any action that's missing.

The policy

Download JSON 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DuskoraReadOnlyChecks",
      "Effect": "Allow",
      "Action": [
        "ecs:ListClusters",
        "logs:DescribeLogGroups",
        "s3:ListAllMyBuckets",
        "sts:GetSessionToken"
      ],
      "Resource": "*"
    }
  ]
}

Every action here is read-only. Deploy runs never get the stored key: Duskora exchanges it for short-lived session credentials with sts:GetSessionToken and hands only those to the run.

When a workflow's Deploy stage turns on Apply infrastructure, the run applies the repository's Terraform with those session credentials. That needs whatever actions your Terraform manages (for example ec2:* or s3:CreateBucket), which Duskora can't know in advance, so they aren't in this policy or the check. Add them for the resources your Terraform manages, scoped as tightly as you can. Session credentials can't call IAM APIs unless MFA was used, so Terraform that manages IAM resources fails with session credentials.

What each action is for

IAM actionChecked withWhat it lets Duskora see
s3:ListAllMyBucketsS3 ListBuckets (one bucket)The account's S3 buckets
ecs:ListClustersECS ListClusters in us-east-1 (one cluster)The account's ECS clusters
logs:DescribeLogGroupsCloudWatch Logs DescribeLogGroups in us-east-1 (one group)The account's CloudWatch log groups
sts:GetSessionTokenSTS GetSessionToken (a 15-minute session, left unused)Short-lived credentials for deploy runs

STS GetCallerIdentity, which checks the key when it's connected, needs no permission.

Attaching the policy

In the AWS console

  1. Open IAM → Users and pick the user whose access key you connect.
  2. Permissions → Add permissions → Create inline policy, switch to JSON and paste the policy.
  3. Name it (for example duskora) and create it.

With the AWS CLI

curl -fsSLo duskora-iam-policy.json https://docs.duskora.ai/aws/iam-policy.json
aws iam put-user-policy \
  --user-name <user> \
  --policy-name duskora \
  --policy-document file://duskora-iam-policy.json

IAM changes can take a few seconds to apply. Reload Settings to run the check again.

What the check reports

Settings runs the check for each connected AWS account, calling each action above with the stored key, and sorts the actions:

  • Missing: AWS refused the call (AccessDenied, AccessDeniedException, UnauthorizedOperation or another HTTP 403). Settings names each missing action and links here.
  • Unknown: the call failed for another reason, such as a network error, throttling or a key deactivated in IAM. Settings shows a note; try again later.

A missing permission doesn't disconnect the account. The check only reads, and its result isn't stored.

Permissions can also be limited outside the user's own policies, by a permissions boundary, a service control policy (AWS Organizations) or a condition on region. If the policy is attached and Settings still reports an action as missing, check those.
